*Part 1 of 2.*

Three days into rebuilding Ghosted, I sent Claude a screenshot. “Spacing and indentation is weird here hopefully should be fix with system rewrite.” I could feel it when I used the app, but I couldn't yet say exactly what was wrong.

Then we counted. Eighteen font sizes, including 11.5, 12.5 and 13.5 px. Nineteen ways of writing a border radius. Twenty-six shadows. On Fit, five different left edges.

I'd approved the edits that got us there. Each had looked reasonable on its own. Seeing them together made me want to stop and work out a system before adding more.

## How it got there

Ghosted is a job-application app I'm building with Claude Code. You paste a posting, tailor a resume on a live canvas, check your fit, research the company and track the application. The rebuild shipped on October 8. By the early hours of October 11, it had 241 commits and 80 release notes, many from parallel agent sessions.

I had deliberately left spacing and components until the layout settled. Color, type and motion had tokens, but padding, radii and shadows were raw values. `app.css` grew to 1,298 lines. Dark mode was written twice.

A global button-hover rule had also reached a specificity of (0,8,1), overriding buttons that were supposed to behave differently.

I could see how we'd done it. I'd ask for a cleaner card, and an agent would choose a padding, gray and radius. Another session would make another reasonable set of choices. I was reviewing the change in front of me, and the differences kept adding up.

At 02:50, I asked to hold the landing-page videos until the system was set up. I didn't want to film an interface I was about to change.

## Put numbers beside the feeling

I asked for an audit across the app and landing page. It listed the values and where they appeared:

| | Found |
|---|---|
| Font sizes | 18 in the app, 29 on the landing |
| Line heights | 10 in the app, 13 on the landing |
| Radius spellings | 19 |
| Shadows | 26 |
| Padding, margin and gap values | 25 in the app, 35 on the landing |
| z-index values | 14 |
| Button class combinations | about 48, plus about 70 state rules |
| Chip implementations | 14 |

The audit also recorded 68 screenshots, covering desktop and phone views in light and dark.

Drawing guides over Fit finally explained my complaint. The left edges sat at 0, 16, 24, 54 and 58 px. A tab panel added padding; a header's text column set another indent for everything underneath it.

## Make the calls together

Claude turned the audit into ten decisions, each with options and a recommendation. I wanted the first code stage to leave the interface looking the same, then make the visible changes separately.

For spacing, a strict 4 px scale covered 54% of the existing values and would move 195 of them. A scale starting at 2 px and then using 4 px steps covered 85%. I chose that.

Text size had been a multiplier, which produced fractional pixels. We made Smaller, Default and Larger modes with whole-pixel values so the choices could also exist in Figma.

Yellow needed a clearer job. It means “the AI changed this” in Ghosted, but the audit found four other uses. I kept it on streaks as a celebration. The New badge and a yellow fix button lost it.

For layout, I chose one left edge per container with the ghost icon inline. Hanging the icon would need a 34 px gutter that phones didn't have.

I accepted the recommendations and asked to consolidate wherever we could. The neutral ramp had 21 grays, chosen separately for light and dark. Four pairs differed by about ΔE 1, so those merged and left 17.

## Keep the decisions in one place

The system starts in `web/src/tokens/tokens.json`, using the W3C design tokens format. It has 59 primitive colors, which nothing uses directly, and 43 semantic colors that refer to them. Light and Dark are color modes; Smaller, Default and Larger are type modes.

Each semantic color has a sentence explaining when to use it. For `ai/highlight`, that's:

> Only 'the AI changed this' (plus the logo and the celebration highlighter). Always a background under ink; same in both themes.

`pnpm tokens` generates the CSS, motion values and brand-guide tables. Claude used Figma's MCP server to build the library from that file too: six variable collections, 14 text styles and five effect styles. A check found no unbound fills or strokes across 306 nodes.

If a decision changes, I edit the JSON, generate the files and sync Figma. The things Figma can't represent, including reduced-motion behavior, `color-mix` tints and breakpoints, are written on a Foundations frame. I want that gap visible to someone opening the file.

## Check the screens while changing them

I needed a way to check the promise that a stage wouldn't change the appearance. We added `pnpm ui:shots`, which starts a server on a throwaway database with a fictional person and three jobs. It captures desktop at 1440 px and phone at 390 px, in both themes, with reduced motion and no AI calls.

Software rendering and a fixed random seed help repeat the screenshots. Comparing before and after normally fails on a single changed pixel. Stage 0 was an exception: merging the grays moved channels by up to 3/255, so that comparison used an explicit tolerance of 3.

The October 11 stages went like this:

| Time | Change | Check |
|---|---|---|
| 03:50 | tokens.json becomes the source; dark mode written once | 56 screens, with the stage 0 tolerance noted above |
| 04:03 | Raw colors and motion timings move onto tokens | Pixel-identical |
| 04:08 | 827 spacing, radius and shadow values move onto tokens | Pixel-identical |
| 04:21 | Fit, Research and the ghost check get one left edge | Intentional visual change |
| 04:30 | 200 font-size declarations move from 18 sizes to eight steps | Intentional visual change |
| 04:53 | Duplicate patterns move onto component specs | Intentional visual change |
| 11:26 | 163 buttons and the pills move onto shared components | Pixel-identical, 58 screens |
| 12:41 | Production release | Live |

There were no commits between 04:54 and 10:44. The screenshot tool also needed fixes: waiting for the resume preview and keeping the product-tour toast out of captures. I needed to trust the comparison before using it to approve a change.

After the release, separate worktrees handled the remaining pieces. A Field component went into five forms. The landing page moved onto the app's tokens. Pills shared one CSS base, empty tabs used EmptyState, and three dialogs moved onto Dialog. Browser `confirm()`, `alert()` and `prompt()` calls became the app's own dialog helpers.

The screenshot set grew to 80 screens. By the end of the day, `web/src/ui` had eight components: Button, ButtonLink, LinkButton, IconButton, Chip, Field, EmptyState and Dialog. The later changes intended to look the same were checked across that larger set.

## Give the next agent a clear fix

I also wanted the next session to know when it was stepping outside those choices.

`pnpm check` now fails on stale generated tokens, new raw hex colors, hand-styled buttons and pills, browser dialogs, or modals built without the shared Dialog. Older raw colors stay in a baseline and come out as they're replaced; new ones fail immediately.

I tried a hand-written button in a scratch edit. The check returned:

```
web/src/App.tsx:407: use <Button>, <LinkButton> or <IconButton> from web/src/ui, not a classed <button>
```

That message tells the agent where to go next. A reminder in a document is easy to miss; a failed check with the component names gives it something to act on.

The guard was 144 lines. It wasn't a git hook. It ran through the project workflow: every session had to run `pnpm check` before pushing, and production waited for a pass.

## What I'd do again

I made about a dozen design calls that day. Agents made the hundreds of edits. When I said to take the remaining recommendations, Claude made those calls and recorded them as open decisions for 1.0. I could still find and revisit them afterward.

The usage sentences mattered too. A person in Figma and an agent in code could read the same explanation of yellow, beside the value they were using.

I don't want to overstate what that proves. This system was used by coding agents and Ghosted's testers. No partner teams had adopted it, and it hadn't been usability-tested. I was trying the method on my own product.

My note that day was that an AI-coded project needs a strong foundation or drift will take hold. But on day one, I didn't know the layout well enough to choose all the tokens. Some would have been guesses.

Next time, I'd still move quickly at first. I'd count earlier, make the decisions together, and add the checks while fixing the drift. Those checks are the part I can carry into the next session without hoping everyone remembers.

## What this used, and what's still open

Claude Code with Claude Opus 5.5 handled the audit, documents, generator and code changes. Figma's MCP server handled the library. Chrome, driven through the DevTools Protocol, handled screenshots. The app used DM Sans, React and Vite; the generator and screenshot script were plain TypeScript with no new runtime dependencies.

The audit started after 02:50 and the system reached production at 12:41 on October 11. The landing videos came back at 13:46, after the interface had settled.

Three motion questions remained for 1.0. Code Connect, to link Figma components to `web/src/ui`, needed a Figma plan I didn't have.

For part 2, I planned to try the same process on a multi-brand system with sub-brands, including packaging and signs. That's a separate story to work through.
