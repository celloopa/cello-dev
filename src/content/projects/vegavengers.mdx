VegAvengers helps people find vegan festivals, animal sanctuaries and advocacy groups. This is how its festival list moved off my to-do list and into an admin its editors run themselves.

## Why did every fix come to me?

<MediaTwo items={[
  { src: "/images/projects/tool-switcher.webm", alt: "The first VegAvengers site switching between festival and sanctuary search", caption: "The first site: festivals and sanctuaries as two modes of one search." },
  { src: "/images/projects/vegfests.webm", alt: "Festival search narrowing results as someone types a city", caption: "Search that works when you half remember: a month name, a city, or UK when you mean England." }
]} />

The first version was a fast, searchable site, and it worked. The festival list behind it kept going out of date.

Festival dates changed. Festival websites went dark. Every correction was a developer task, so every correction was mine.

The question became who keeps that list true, and how much of it should need me at all.

## Let the dates stay messy

<MediaFull
  src="/images/projects/cms/cms-festivals.webm"
  alt="The festival list in the admin, showing one festival's 2025 and 2026 editions as separate records"
  caption="One festival, two years. Last year's edition is confirmed and published. This year's is still to be announced, with a suggested update waiting as a draft."
/>

Festivals announce dates like "6/5-6/7/26", "TBD" or "sometime in the fall". I wanted the content model to take that as it comes.

Each record keeps the date exactly as the festival wrote it. Where the date is clear enough, it also stores it as a calendar date. Visitors see what the festival said, and search can still sort by date.

Each year's festival is its own record. Next year starts as a copy, and last year's stays as history.

Every record also says where it came from: a spreadsheet import, a person, or the checker. Editors can't change the fields the checker fills in, so they can see at a glance which parts are the checker's and which are theirs.

## Show the editors only what they need

<MediaFull
  src="/images/projects/cms/cms-editorial.webm"
  alt="An editor writing a photo-essay post, then browsing the media library where each image has a credit"
  caption="Writing a photo essay, then finding its images in the library, each with its alt text and credit."
/>

The admin came with far more than the editors need, so most of my design work there was taking things out.

I cut the formatting buttons down to meaning: emphasis, links and structure. The templates handle how it looks, so nobody fights alignment buttons at midnight.

Every photo in a gallery carries a credit. The first real post was a photo essay, and crediting each photographer was part of publishing it.

The festival list and the blog sit in different places in the admin, because they're different jobs.

## How does the checker spot a stale date?

<FlowDiagram
  title="A suggestion becomes a draft"
  items={[
    { label: "Read", detail: "Open the festival's own website, the source an editor would check." },
    { label: "Ask", detail: "Ask the AI one question: is next season's date posted here? Ordinary code checks the answer before it gets used." },
    { label: "Compare", detail: "Compare it with the published record. If nothing changed, note the check and move on, with nothing for anyone to review." },
    { label: "Draft", detail: "Write the change as a draft, with the suggested date and the text it found quoted as evidence." },
    { label: "Publish", detail: "An editor compares the versions in the admin they already use, and publishes or doesn't." }
  ]}
  caption="Every suggestion waits as a draft on the festival's own record."
/>

The checker goes after the original problem. It visits each festival that's still waiting on a date and looks for a new one.

A dead link gets flagged in a draft too, and a second check tries the link again later. The checker never makes up a new link.

## Where does an editor say yes?

<MediaFull
  src="/images/projects/cms/cms-draft-review.webm"
  alt="Reviewing the checker's draft on a festival: its notes, the version history and the side-by-side comparison"
  caption="A real check on live data: the dead-link evidence in the notes, the version history, and the comparison an editor reads before publishing."
/>

I could have built a separate review screen. I had the checker write ordinary drafts instead.

The editors already knew the draft and compare screens. A suggestion from the checker looks like a colleague's unpublished edit, with the evidence attached, and approving it is one click.

## What broke before launch?

Before the checker touched live data, I put it through a review whose only job was to break it. The review found real problems.

The worst one was quiet. When the checker found nothing new, it updated a note on the published record. That small update could bury a draft an editor hadn't published yet, and nobody would see it go.

Now the checker looks for a waiting draft before it writes anything.

Then I ran it against the live site. A festival with a dead link got its draft, the second check added its evidence, and the published page stayed exactly as it was until a person decided.

## Who runs it now?

The editors do. When one of them publishes, the site rebuilds itself. If the CMS is ever down, the public site and its search use a saved copy of the content. An outage can make the site less fresh, but it can't take it down.

The festival list has owners, and each fact has a record of where it came from.

It also sharpened an idea I keep coming back to, the same one [Ghosted](/projects/ghosted) taught me from the other direction. Give code everything it can do. Give the model the smallest job it can be trusted with. And put a person's approval exactly where the consequences are.

In a CMS, that place is publish, so that's where this system puts it.
