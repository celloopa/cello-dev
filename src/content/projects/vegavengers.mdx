## Context

VegAvengers is a mission-driven platform for connecting people with vegan festivals, animal sanctuaries, and advocacy organizations. The first product-design problem was discovery: visitors may not know the exact event name, sanctuary name, country spelling, or month format they need.

The second problem arrived after the public experience shipped. Editors needed to publish articles, update yearly festival data, manage media and credits, and keep hundreds of resources current without touching code. I expanded the product from a front-end project into a two-sided system: a fast public Astro site and a separate Payload workspace built around the editorial workflow.

## User Scenarios

- A visitor remembers that a VegFest happens in March, but not the event name.
- Someone searches for `UK` and expects to see results from the United Kingdom, England, or GB.
- A traveler wants to find animal sanctuaries by region rather than by exact name.
- A supporter wants to browse advocacy projects and quickly understand which organizations to visit.
- An event listing has an uncertain date, so the interface needs to show TBD without burying it.
- An editor needs to correct a date, publish a story, or credit a photograph without waiting on a developer.
- The CMS is briefly unavailable, but visitors still need a working public site and search fallback.

## Product Decisions

**Flexible query handling.** Search supports month names, month numbers, location synonyms, and region matching because real users rarely search with clean database terms.

**Mode switching over separate pages.** The ResourceToggle lets users switch between VegFest and sanctuary discovery without losing the sense that both are part of the same resource system.

**Temporal result states.** VegFest results are categorized into upcoming, TBD, and past events so uncertainty is visible instead of hidden.

**Motion as feedback.** Framer Motion supports mode changes, staggered cards, and hover states. The goal was not decoration; it was helping the interface feel responsive and alive while users browse.

## Evolving The Content System

I kept the public site in Astro and built the editor workspace as a separate Payload application. That preserved the working visual experience while giving editors structured collections for posts, projects, team members, media, festivals, sanctuaries, and site-wide content.

**Static editorial, live resources.** Editorial pages are prerendered for speed and resilience. Search routes read published resource data from Payload with a short cache, then fall back to Astro DB if the CMS URL is missing or a request fails.

**Prove parity before changing the source.** I extracted the existing search behavior into data-source-agnostic functions and built a comparison harness against live Payload data. The route swap happened only after the old and new sources produced equivalent results for representative months, synonyms, regions, and pagination.

**Protect the public experience from CMS downtime.** Build-time editorial getters retain a fixture fallback. A temporary CMS failure can produce an older but working site instead of a failed build or blank page.

**Bound staleness deliberately.** Publishing meaningful content requests a debounced Netlify rebuild. Media rules avoid rebuilding for every upload or credit correction, and a nightly GitHub Action provides an independent backstop so skipped or dropped hooks cannot leave prerendered content stale indefinitely.

**Make media operational, not decorative.** Payload stores required alt text and reusable photo credit with each media item; Cloudflare R2 serves generated image sizes. Blog templates own layout while editors own the story, links, captions, and attribution.

## Outcome And Learning

VegAvengers now runs as a live hybrid platform: the public Astro site is deployed on Netlify, the Payload workspace and PostgreSQL service run through Coolify, media is stored in Cloudflare R2, and resource search has a verified fallback path.

The strongest lesson was that product reliability spans both sides of the experience. For visitors, it means forgiving search and clear temporal states. For editors, it means understandable content models and safe publishing. For the system, it means defining what may be stale, for how long, and how the product behaves when one service is unavailable.

The remaining opportunity is measurement. I would add privacy-conscious analytics for common queries, no-result searches, resource-mode usage, and editorial publishing time instead of inventing outcome metrics from launch alone.
