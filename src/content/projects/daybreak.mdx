## Context

Most planning tools ask you to maintain the system before the system is useful. I wanted Daybreak to start from the other end. It should work out a believable starting point from what it already knows, bring the plan to you, and make reviewing it lighter than planning from scratch.

Daybreak is a personal app. I designed it, I built it, and I'm the one using it every day, so read this as personal dogfooding rather than a product tested with users.

The harder design problem showed up when I added an AI agent. A chat interface is only useful if it can change the same real state as the UI. And it's only trustworthy if it can't quietly get around the UI's rules. I treated that tension as the core of the product's architecture, not a chat layer added at the end.

## Product principles

**Computed over asked.** Daybreak works out a starting plan from projects, tasks, routines, due work, carry-over and fixed Calendar constraints. You review and correct it instead of rebuilding the day by hand.

**Honest over optimized.** A useful plan can look incomplete. Work that doesn't fit stays on deck. It doesn't spill past midnight or hide behind a false sense that everything's handled.

**Editable over autonomous.** Generated blocks are ordinary things in the app. You can move, remove, defer or complete them directly, and your manual edits always win.

**One product, two interfaces.** A feature isn't done when only the visual UI can use it. The agent needs a typed path to the same operation, or a written-down reason it shouldn't have one.

Right now the registry has 42 typed operations. Twenty-seven are open to the chat agent. The other fifteen are left out on purpose, wherever confirmation, privacy, data a provider owns, or destructive behavior still needs a stronger product policy. A separate inventory covers 38 changes people can make in the UI: 30 map to agent operations, and eight are explicitly excluded.

Those exclusions are part of the design. The agent can complete an eligible task, for example, but deleting things stays out of chat. It can plan around imported meetings, but it never rewrites a Calendar event that belongs to the calendar. A traffic workflow can use a provider's result, but the model can't make up a travel estimate.

## Planning around reality

Calendar events come into Daybreak as pinned constraints, and they keep track of where they came from. Daybreak's own work can move around them; the source meetings can't move. If an event is missing, Daybreak only treats that as evidence inside the exact Calendar window and account it scanned.

Daily planning leans on evidence the same way:

- Unattended imports can relax a due date, but never make work more urgent.
- Working ahead fills time that's genuinely open. It doesn't push out due or carried work.
- Work that can't fit before the end of the local day stays unscheduled and visible.
- Completing a blocker puts a dependent task back in its previous state instead of inventing progress.

## Designing through dogfooding

I use Daybreak to run my actual days. When something confuses me, I trace it back through the interaction, the state and the code.

One live late-start session turned up twelve prioritized issues. The plan didn't acknowledge a delayed start clearly enough. Carry-over counts could feel unstable. And state across devices could shake my trust, even when the merge underneath was technically right.

That session changed where the product was going. Evening prep now does more of the heavy lifting. Morning review is meant to stay light and work well on a phone. Recovering from a late start has its own state. And I treat sync being correct as part of the experience, not background plumbing.

## Outcome and limits

Daybreak runs as a signed Mac app and on a physical iPhone, with private CloudKit sync, typed task and plan operations, unattended workflows, a native agent chat and a receipt for every change.

The most useful thing I got out of it is a rule the system made concrete. AI should extend a designer's tools without taking away their taste, their ownership or their ability to fix the result. Reliability here isn't only about model quality. It's how clearly the interface shows uncertainty, who owns each piece of state, and what happened after you asked for a change.

It's still a personal product that I'm dogfooding. Distributed claiming across multiple Macs and some external-write policies are documented follow-ups. And I'd want to validate the planning model with more people before treating my own routine as something that works for everyone.
