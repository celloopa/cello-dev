## One system, three brands

I lead design for three cannabis brands: Asheville Dispensary, Plantbar and Nightshade. Each one has to look like itself, but I didn't want to design three of everything.

So they all come out of one shared Figma system, with one simple rule. The structure is shared, and each brand brings its own identity.

Here's the same portal in all three brands: one layout, one set of components, one search. The color comes from each brand's own tokens.

**What stays shared:**
- Spacing and layout patterns.
- Components: cards, category tiles, search and forms.
- How things are organized: brands, categories, tags.

**What changes with each brand:** its color, set by the brand's own tokens (CSS custom properties in code).

### From Figma to production

- **The drop card.** The social story card is a component in the Figma system. The pipeline below fills in its slots (strain, tier, sale wording, photo) and never touches the layout, so every card that goes out is the design I approved.
- **The web store.** I design UI components and ship them into WordPress as custom PHP and JavaScript plugins, so the mockup and the live store stay the same thing.
- **The asset directory.** The brands' approved assets used to live across Drive folders, bookmarks and memory. Now they have one searchable home. Its portals share one component system and switch identity through CSS custom properties instead of duplicated code. Admins who aren't developers manage brands, categories and links themselves. The data lives in Supabase with a JSON fallback, so the directory still works when the database doesn't.

## The flower drop pipeline

The biggest payoff so far is a tool built on top of the system. Two or three times a week, the ecommerce team announces a flower drop, and every strain needs a branded story card and a short vertical video. By hand, that took seven tools and 3–5 hours a week.

I approach everything I build here the same way. Code does everything it can do exactly. A model gets the narrow piece that needs judgment. And a person approves anything that reaches other people.

### Code first

The first live run picked the wrong strain. Search returned a lookalike, and a stale sitemap pointed at an old product page.

I didn't fix that with a better prompt. I fixed it with more code. The scraper now tries the likely product URLs directly, rejects any page whose title doesn't match the strain, ranks what's left by tier and publish date, and logs why it picked each one. The call I used to make in my head ("I just know which page is right") became a rule anyone can read.

Premiere went the same way. When I actually opened the template, it was a card image with a product video masked into a circle: 4.73 seconds, no animation. That's a recipe, not an edit. I pulled the circle's geometry from a frame of an old export and the encoding settings from its metadata. Now one ffmpeg command renders each story in seconds. It also fixed a quiet bug: the old exports were set to "no audio" but still carried a stray audio track.

### The day it sent too early

In late July, the routine posted a card with the wrong tier. The announcement said one tier, but the product page sat under another, because a new page used a URL pattern the scraper didn't know yet. The agent noticed the conflict, logged it politely, trusted the website and posted anyway.

Undoing it meant deleting an attachment, deleting a Slack file by hand and threading a correction. Everything before the post would have been free to fix. I came out of that day with three rules:

- **The announcement decides the tier.** The site supplies media, never categories. A mismatch gets logged loudly and never adopted.
- **The scraper knows both URL patterns.** That alone would have caught it.
- **Completeness gate.** If any strain in a drop is unfinished, held or unresolved, nothing gets sent. Finished files attach quietly, and the post waits until the whole drop is ready.

A go-live guard covers the opposite case. If a drop is announced for tomorrow, the task gets created now and the media waits until the pages actually go live.

### Paying for the model only when there's work

Most scheduled checks find nothing. Drops land between about 3 and 8 a.m. Pacific, and most days don't have one. Every check was still opening a full agent session just to look at Slack. At its worst, with the task drifted onto a top-tier model, an idle day cost about $12.10.

So I timed every announcement from the first two weeks and redesigned around that data instead of my guess. The schedule went from seven checks a day to three, placed where drops actually land.

A zsh script now decides whether there's work before any model gets involved. Its exit codes are the interface: work, idle, done for today, or error. An error fails open, so a broken token can't silently skip a drop. A small model only dispatches. On a drop morning, it hands the run book to a stronger model that does the real work.

An idle day now costs about $0.30. A drop day adds one $6–8 pass that takes 10–14 minutes, and that's where I want the money to go.

Cost reporting reads the agents' own transcripts after the fact, so nothing in the pipeline has to report on itself. That's also how I caught the drift. The run book doesn't set the scheduled model, so I have to check it instead of assuming.

### Record

From July 9 to October 8, 2026: 69 archived runs, 37 drops delivered end to end, and no failed runs. The partial runs are the go-live guard holding media for pages that weren't live yet. That's the guard doing its job.

## What's next, at its real stage

The same split carries into the rest of my design work. These are at different stages, so I'll describe them that way:

- **Print coordination: prototype.** A local intake and status tool for getting approved artwork to a print vendor and picked up. It keeps artwork, cost and vendor-release approvals separate. A revision cancels the approvals it touches. "Ready" never counts as "picked up." It runs on simulated vendor events and isn't connected to anything live yet.
- **Presentations from approved templates: planned.** An agent fills the content slots of decks I've designed and approved. It never invents a layout, and I review every deck.
- **Packaging checks against compliance checklists: planned.** Compare new packaging artwork against the team's existing checklists and write a gap report for the people who own compliance. It only reads; it doesn't change anything.

## What I learned

Honestly, the automation itself was rarely the hard part. The hard part was deciding what the system is allowed to believe (the announcement, not the website), what it can do on its own (anything that can be quietly redone) and when it has to stop and wait (anything other people will see).

Once I wrote those down as rules, the model's job got small enough to trust.
